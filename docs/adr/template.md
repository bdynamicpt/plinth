# N. The decision, as a short sentence

- Status: proposed | accepted | superseded by [ADR M](000M-….md)
- Date: YYYY-MM-DD
- Issue: [#n](https://github.com/bdynamicpt/plinth/issues/n)

## Context

What forces the decision: the problem, what Plinth already has, and the constraints (the
component rules in `CONTRIBUTING.md`, earlier ADRs, the browsers and frameworks Plinth targets).
Say it so a reader who wasn't there can follow. No consumer project's name, colours or copy:
Plinth is public and serves several projects.

## Decision

What Plinth does, stated plainly enough to check a pull request against. Use subsections for
the parts of a larger decision, and tables or short examples where they are clearer than prose.
Name the options that were set aside, and why, when a reader would otherwise ask.

## Consequences

What follows from the decision, good and bad: what changes in the code and the docs, what is now
harder, and what is left open (with its issue).
